# 我们在"记忆治理"上拿了全榜第一，而我们的系统没有治理机制

**ActiveMemoryIndex · Agent Memory Leaderboard 首期开源榜第 3 名**

AML 团队在邀请函里注意到，我们在"新值覆盖与当前状态判定"（54.50）和"矛盾检测与冲突消解"（24.79）两个细项上位列全榜第一，并推测这背后是"一条强调时间、状态更新和冲突治理的技术路线"。

这个推测很自然，但它不成立。我们必须先把这件事说清楚，否则后面的内容都建立在一个错误的前提上。

**ActiveMemoryIndex 的存储层只有两种 SQL 动作：`CREATE` 和 `INSERT OR REPLACE`。没有一条 `UPDATE`，没有一条 `DELETE`。** 系统从不更新记忆、不合并记忆、不让旧记忆失效、不检测矛盾、不做冲突消解。写进去的每一条记忆永远有效，彼此完全平权。代码是公开的，这一点可以直接核验。

所以真正的问题不是"我们怎么做的治理"，而是：**一个完全不做治理的系统，为什么会在治理细项上排第一？**

我们不确定完整答案，但手上有一些可以公开的证据，指向一个不太舒服的结论。

---

## 一、我们实际造了什么

一句话：**一个尽量不丢失信息的检索器**。

**双写。** 每个 Add 请求（最多 20 条消息）被存两份：逐字原文（带时间戳前缀）和 gpt-4o-mini 抽取的第一人称原子事实。两份都用 `bge-small-en-v1.5` 嵌入，存进同一个 SQLite。

**第一人称回忆句检索。** 检索时把问题改写成用户自己口吻的回忆问句（"我有没有跟你说过……"），把它的嵌入和原查询的嵌入融合后排序。

需要明确说明：**这就是 HyDE**（Gao, Ma, Lin, Callan, 2022, arXiv:2212.10496），N=1 的情况。因为分数融合 `(1-w)·(q·d) + w·(r·d) = ((1-w)q + w·r)·d`，加权相似度和嵌入平均在数学上是同一个操作，而 w=0.5 正是 HyDE 论文里的默认形式，也是主流 RAG 库的默认行为。我们独有的只是那个 prompt——生成回忆**问句**而非假想**答案**，因为语料是第一人称聊天记录。把它当成新方法是不诚实的。

**原文优先排序。** 返回的记忆按"逐字原文在前、抽取事实在后"排列，各自内部保持相关度顺序。这一步只改顺序、不改集合。

**邻居窗口（提交后才加）。** 每条命中的原文连同它前后各一条一起返回。

**没有的东西：** 图、层级摘要、实体消歧、任何形式的记忆治理。

## 二、我们测掉了自己的三个想法

这个项目里真正花时间的不是造东西，是**拆掉自己造的东西**。

**混合检索（BM25 + 稠密，RRF 融合）——建了、测了、删了。**
它有效：端到端 +1.8 分。但一个对照臂让它出局了——把 BM25 限制在逐字原文通道上得到 .6390，而**纯粹把原文排到前面**（一个排序键，不需要索引、不需要查询语言、不需要融合规则）得到 .6333，落在前者三次重复的离散区间内。整套 FTS5 换来的东西，一个 `ORDER BY` 就有。我们删掉了它。

（有意思的是，本期榜单上能读到源码的参赛系统里，多数正是"BM25/FTS5 + RRF"。我们不认为这证明谁对——只说明我们那次删除有实测依据。）

**父块返回——测了，分数更高，没有上。**
把命中项所在的整块 20 条消息一起返回，得分 **.711**，比我们提交的 .6333 高 7.8 分。我们没有用它。

原因是一个等预算对照：把父块砍到和基线相同的字符数，它只有 **.572**——比基线低 6.1 分。**粗粒度单元本身是负贡献，全部收益来自 5.4 倍的内容量**，而内容量能涨是因为契约的 `top_k` 只限**条数**不限**大小**。

我们还发现，在这个契约下**体积和粒度在数学上不可分离**：100 条上限下，用单条消息最多只能凑到约 12.4k 字符；想返回更多文本，就必须把"一条记忆"定义得更粗。而这条路的极限是合法的退化解——一段 LoCoMo 对话约 40 块，全返回就是逐字交出整段对话，条数 40 ≤ 100。

所以 .711 测量的不是记忆能力，是我们被允许花掉多少阅读器上下文。我们把它写进仓库（`bench/results/granularity_audit.txt`）并放弃了那 7.8 分。

**这里有一个给 AML 的具体建议：在条数上限之外增加 token 上限，或者在榜单上把 tokens/query 与准确率并列公布。** 先例是 TREC QA 把答案串从 250 字节收紧到 50 字节，理由完全相同——每一个同时提交两种长度的机构都是 250 字节得分更高。

**检索指标在我们的实验里与准确率反相关。**
我们跑了七个只改返回顺序或组成的臂。覆盖率@100 最高的那个臂（.961）准确率最低（.5625）；准确率最高的臂覆盖率@20 全场最低（.609）。**我们曾经把覆盖率阈值预注册为上线判据，而它会选出最差的那个配置。**

原因不复杂：这些臂返回的是同一批证据，而"证据在不在返回集里"这个指标按定义看不见顺序。我们记下这件事，是因为它对任何用 recall@k 做决策的人都成立。

（这个现象本身不是我们的发现，Song et al. arXiv:2601.17532 的摘要已经写了检索指标可能与端到端质量负相关；也有工作报告相反结论。我们只是记录了自己这组臂上的观测和它对决策程序的破坏。）

## 三、回到那个问题：为什么不做治理反而治理分最高

我们只能给出一个有证据支撑的假设，不能给出结论。

**假设：把完整、带时间戳、未经改写的原始记录交给阅读模型，让它自己判断哪条还有效——比我们代替它判断要好。而做一半的治理，比不做更糟。**

第二半有旁证。本期榜单上有一个参赛系统（FlowGrid）确实实现了治理：标注冲突、给旧值降权、但不删除。它在自己的 README 里测出**陈旧值泄漏率 0.53**，而它的记忆治理轴得分 **27.86，是学术榜前十里最低的**。我们完全不做治理，得 **37.95，最高**。

如果这个对比不是巧合，那么它说的是：**治理的价值在于真正改变"返回什么"，而不是改变分数权重。** 标注和降权把判断责任留在了中间层，却没有能力承担它——旧值仍然进入上下文，只是排得靠后一点，阅读模型照样会读到。

我们自己的实验也从另一个方向支持"信息完整性"这条线：只用抽取事实的臂得 **.513**，只用逐字原文的臂得 **.624**。抽取是有损的改写；**我们每次 Add 花掉的那次 gpt-4o-mini 调用，净贡献大约只有 0.9 分**。这和独立工作（arXiv:2601.00821）在 LoCoMo 上的结论一致：原文块 43.9%，原文∪抽取事实 42.5%，McNemar p=0.39，无差别。

顺带一个也许有用的观察：**本期开源榜第一名 InvMem 的仓库自述是"一个朴素 RAG 基线"，在记忆链路上一次 LLM 都不调。** 我们每次 Add 调一次抽取、每次 Search 调一次改写，比它低 0.22 分。这值得整个社区想一想。

## 四、我们做错的地方

**一个推广错误，是在读第一名的公开代码时发现的。**

榜单公布后我们去读了开源榜前几名的仓库。第一名 InvMem 的默认配置里有一行：

```
MEMORY_RESULT_WINDOW=1
```

每条命中的记忆连同前后各一条一起返回。我们当时的反应是"这不就是我们否掉的那个东西吗"——因为我们测过父块返回，并因为它是体积效应而放弃了它。

但这两者不一样，而分辨它们本来是我们的责任。我们从"父块在等预算下更差"（4.9 个来源块对 26.2 个来源块，差 6.1 分）得出"广度是硬约束"，然后用这一条否掉了**整个"扩展返回单元"的技术族**。

这个推广是错的。正确的说法是：**广度在极端处有约束，在中间区间没有。** 我们照着测了一遍"每条命中带前后各一条邻居"——同样 100 条、字符只多 8%、来源块从 26.2 降到 20.9——得到 **.6802，比提交版本高 4.7 分（n=1540，配对 p<0.0001）**，其中时序类涨 5.3 分。半径 1、2、3 之间统计上无法区分。

而首期开源榜前十的总跨度只有 2.10 分。

预测这件事所需的全部要素当时都在我们手上：我们已经测出"等体积下广度打赢完整性"，而一条邻居恰好是**几乎不损失广度地补上局部上下文**。我们只是没走完最后一步，直到别人的代码把它摆在面前。这个改动现在已经上线，代码和数据都在仓库里。

**这是开源榜最直接的价值**——不是排名，是十份可以互相拆开来读的实现。我们从第一名那一行配置里学到的东西，比我们自己在提交前五天里做的全部消融加起来还多。

**还有一次是方法论上的：** 我们让两个子智能体分别归因"变好的题"和"变坏的题"，给前者的指令强调了"噪声占比是最重要产出"。它报告 51% 是噪声，后者报告 24%。后来用同配置重复跑测出客观噪声占比是 24%——**前者的偏差是我们在提问方式里喂进去的**。任何用模型做评估的人都值得留意这一点。

## 五、关于名字：为什么现在这一版并不 active

这个系统叫 ActiveMemoryIndex。名字里的两个词来自底层研究的两半，而这次提交的只有其中一半。

**Active 指的是"写进权重的记忆"。** 底层研究 *An Index, Not a Store: The Model Does Remember — It Just Needs Its Notebook* 的主体是**在线权重级学习**——把新知识用 LoRA 适配器直接写进一个本地 9B 模型的权重里，让**模型本身成为存储**，检索则是从权重里唤起回忆。这才是"主动记忆"的原意：记忆不是躺在外部索引里等人来查，而是变成模型的一部分。

**而这次提交里没有这一半。** 赛事规则要求 `gpt-4o-mini` 是 Add 和 Search 期间使用的唯一模型，所以论文里最强的配置（9B 骨干 + LoRA r=32）、EWC 正则、Benna-Fusi 级联、按用户划分的权重分区，**全部被排除在提交之外**——不是我们放弃了，是这个契约在结构上容纳不了权重级记忆。

于是出现了一件我们提交时就知道、但现在才觉得值得说的事：**我们那套 Add/Search harness——双写存储、register-matching 检索——原本是为了在 InMind 基准上测量那个权重级系统而造的对照工具。我们拿去参赛的，是当初用来做测量的仪器，不是被测量的东西。**

所以 Index 那一半是站得住的，而且是这次结果里最经得起检验的部分：模型不缺知识，缺的是索引；记忆系统的职责是把模型已有的能力重新指回正确的位置。我们所有赢分的改动都落在"别丢失原始记录、并把它放在读得到的位置"这个方向上。

**Active 那一半在这次提交里是名不副实的**，而且原因不在我们的实现质量，在参赛边界。这一点值得 AML 知道：**当前契约把"模型即存储"这一整类架构排除在外了**，榜单目前测量的是外部索引这一族。这不是批评规则——固定生成模型才能公平比较记忆系统——只是说明这张榜的覆盖面。

顺带一提，"主动"还有一个更弱的含义：系统在**检索时**主动做事。我们确实建了这类部件，而它们也全被自己的实验拿掉了：

| 部件 | 结局 |
|---|---|
| agentic 反思 + 第二轮检索 | 端到端零增益，**默认关闭**。后来还发现它的合并路径会绕过原文优先排序，等于静默撤销一个实测 +4.5 分的改动 |
| 混合 BM25 通道 | 有效但被一个排序键支配，**整套删除** |
| 第一人称回忆句改写 | 就是 HyDE；保留，但它是借来的，不是我们的 |
| gpt-4o-mini 抽取事实 | **净贡献约 0.9 分**，而它是每次写入都要付的成本 |

而真正拿到分的是三件**被动**的事：不要丢掉逐字原文、把原文排在阅读模型先读到的位置、返回时把相邻的一两轮一起给出去。**没有一件是"主动"的**——它们全都只是不破坏、并妥善呈现已经存在的东西。

所以准确的说法是：**这个名字描述的是一条完整的研究路线，而这次提交是它在赛事约束下的合规子集。** 我们不打算改名——权重级那一半仍然在做，只是它不能进这张榜。

但也不该让名字替提交说话。**在这次评测里，ActiveMemoryIndex 是一个 index，不是 active 的。**

## 六、接下来

**时序是我们最弱的一轴（C = 18.35），而整个开源榜集体困在 18–24.6，工业榜前两名是 56–60。** 这不是我们一家的问题，是这一类方法的共同边界。

我们读过的所有公开参赛系统处理时间的方式都是：把时间戳当前缀贴在文本上、正则抓年份、或者按**插入时间**做指数衰减。这些都不是时序推理。

我们接下来要做的是**写入时把相对时间表达解析成绝对时间，并给事实加版本**。它同时打 C 和 A（时间锚定错了，事实召回也跟着错），而且它在写入层——正是我们从来没碰过、整个开源榜也集体空白的那一层。

有意思的是，这会把我们推向 AML 邮件里最初描述的那条路线。只不过现在我们知道，那句描述**当时**是不准确的，而如果将来准确了，那是因为我们真的去建了它。

- 引用与致谢：HyDE（arXiv:2212.10496）、query2doc（arXiv:2303.07678）、small-to-big / passage-level evidence（Callan, SIGIR 1994）、LoCoMo（arXiv:2402.17753）、AML 公开评测代码

**口径说明：** 本文中除榜单分数外的所有数字，均来自我们自己的离线复现——公开的 `locomo10.json`、我们自己的裁判、n=1540、每臂 2–3 次独立重复。它和 AML 的评测是两把不同的尺子，只应作为**配置之间的排序**参考，不应与榜单分数直接换算。文中引用的 54.50 与 24.79 两个细项分数来自 AML 邮件，公开榜单 API 只提供到轴级，我们无法独立核验。

**关于团队与 AI 协助：** ActiveMemoryIndex 由 Xuhao Lin（独立研究者）提交。实际的工作方式是一人加一个 AI 协作者（Claude）：代码、实验设计与本文初稿在协作中产生，全部实验在作者自有硬件上执行、由作者核验，所有取舍——上线什么、放弃什么、哪些分数不要——均由作者判断。

这种分工不是形式上的。本文记录的几处错误里，有两处是 AI 协作者犯的：把一个在极端点上成立的结论外推到中间区间（因此漏掉了邻居窗口），以及在给子智能体的指令里喂进了偏差（导致 51% 对 24% 的噪声估计分歧）。而促成最大一处改进的观察——去看第一名仓库里那行 `MEMORY_RESULT_WINDOW=1`——来自作者。

我们把这些写出来，是因为一份声称"由 AI 协作完成"的技术报告，如果不说明协作在哪里出错、又在哪里被人纠正，那份声明就没有信息量。
